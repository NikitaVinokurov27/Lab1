# ADR-001. TimeSpent: учёт и показ объёма учебной работы ребёнка в родительском кабинете

- **Статус:** Принято (для проверки гипотезы через A/B)
- **Дата:** 2026-07-16
- **Команда:** МИВТ-25-3 — Винокуров Никита, Данильчатенко Евгений, Чекмарёв Данила
- **Кейс:** VK × Учи.ру — «Сколько работы проделал ребёнок»

---

## 1. Контекст

Родитель приносит деньги (полный доступ), но слабо вовлечён в процесс на Учи.ру. Кабинет уже
содержит много данных о заданиях, темах, ошибках и программе, **но родителю сложно за 10 секунд
понять объём проделанной ребёнком работы** — картину нужно самому собирать из разных блоков.

**JTBD родителя:** «Когда мой ребёнок занимается самостоятельно, я хочу за 10 секунд понять,
сколько реальной работы он уже сделал, чтобы решить, стоит ли поддерживать это полным доступом».

**Главная гипотеза:** если показать родителю объём уже проделанной ребёнком работы в понятных
единицах (часы → «школьные уроки»), родитель чаще заинтересуется кабинетом и полным доступом.

Чтобы гипотезу можно было проверить, нужен технический механизм, который **достоверно измеряет
активное учебное время** и агрегирует его в недельный итог. Этот ADR фиксирует, как именно
время записывается, считается и хранится.

---

## 2. Рассматриваемые варианты учёта времени

| Вариант | Как считает | Почему не подходит / подходит |
|---|---|---|
| **A. Время сессии = `logout − login`** | Разница между входом и выходом | Завышает: вкладка открыта ≠ ребёнок занимается. Не отражает реальный труд. Отклонено. |
| **B. Сумма длительностей заданий** | Складываем время внутри решённых заданий | Теряет чтение теории, разбор ошибок, паузы на подумать. Занижает. Отклонено. |
| **C. Heartbeat + idle threshold** ✅ | Клиент шлёт «пульс» пока есть активность; простой отсекается | Меряет **активное** время близко к реальному труду, устойчиво к «открытой вкладке». Принято. |

**Решение: вариант C.**

---

## 3. Решение

### 3.1 Модель событий

Клиент (экран ребёнка) эмитит поток событий. Каждое событие: `{ child_id, ts, type, payload }`.

| Событие | Когда | Зачем в метрике |
|---|---|---|
| `lesson_open` | Ребёнок открыл урок/задание | Начало активной сессии |
| `heartbeat` | Каждые `HB = 15 c`, пока есть активность (клик/скролл/ввод/ответ) | **Основной источник активного времени** |
| `task_done` | Задание завершено | Счётчик «заданий» |
| `error_review` | Ребёнок разобрал ошибку | Счётчик «ошибки разобраны» |
| `attempt` | Повторная попытка задания | Счётчик «повторных попыток» (индикатор усилий) |

> В демо-прототипе `HB = 2 c` (ускорено, чтобы таймер было видно вживую за секунды).

### 3.2 Как считается активное время (ядро TimeSpent)

Активность на клиенте отслеживается по пользовательским событиям (`mousemove`, `keydown`,
`scroll`, ответ в задании). Пока они приходят — идёт «пульс»; их отсутствие дольше порога = простой.

```
IDLE_THRESHOLD = 60 c          # нет активности дольше — пауза, время не капает
HB              = 15 c          # период heartbeat
LESSON_MINUTES  = 45           # 1 «школьный урок»

# Активное время за период (сервер, при агрегации):
active_seconds(child, week) =
    Σ по heartbeat-сессиям ( min(gap_до_следующего_hb, IDLE_THRESHOLD) )

active_minutes = active_seconds / 60
school_lessons = round(active_minutes / LESSON_MINUTES)   # 275 мин / 45 ≈ 6 уроков
```

Ключевая идея: время между двумя соседними heartbeat засчитывается, только если разрыв не
превышает `IDLE_THRESHOLD`. Ребёнок отошёл → следующий пульс придёт нескоро → пауза не
засчитывается. Это и есть «активное время без простоя» со слайда архитектуры.

### 3.3 Схема хранения

Гранулярность агрегата — **(child_id, week_id)**. `week_id` в формате ISO `YYYY-Www` (напр. `2026-W29`).

```sql
-- Сырой поток (append-only, для пересчёта и аудита)
CREATE TABLE learning_events (
    id         BIGSERIAL PRIMARY KEY,
    child_id   UUID        NOT NULL,
    ts         TIMESTAMPTZ NOT NULL,
    type       TEXT        NOT NULL,   -- lesson_open | heartbeat | task_done | error_review | attempt
    payload    JSONB
);
CREATE INDEX ON learning_events (child_id, ts);

-- Недельный агрегат (то, что читает виджет; пересчитывается из событий)
CREATE TABLE effort_weekly (
    child_id        UUID    NOT NULL,
    week_id         TEXT    NOT NULL,   -- 2026-W29
    active_seconds  INT     NOT NULL DEFAULT 0,
    tasks_done      INT     NOT NULL DEFAULT 0,
    errors_reviewed INT     NOT NULL DEFAULT 0,
    retries         INT     NOT NULL DEFAULT 0,
    active_days     INT     NOT NULL DEFAULT 0,   -- число календарных дней с активностью
    by_day          JSONB   NOT NULL DEFAULT '{}',-- {"mon":45,"tue":55,...} минуты по дням = «Ритм недели»
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (child_id, week_id)
);
```

Агрегат обновляется инкрементально при приёме событий (или пересчётом джобом раз в N минут).
Сырьё `learning_events` хранится, чтобы можно было пересчитать при смене правил (`IDLE_THRESHOLD`,
`LESSON_MINUTES`) без потери истории.

> В прототипе роль обеих таблиц играет `localStorage` под ключом `uchi_effort_v1` — та же схема
> `(child_id, week_id)` и те же поля агрегата, чтобы механизм читался буквально по коду.

### 3.4 API

```
GET /parent/effort-summary?child_id={id}&week_id={YYYY-Www}
```

Ответ — данные виджета (без сырых событий, только агрегат):

```json
{
  "child_name": "Саша",
  "week_id": "2026-W29",
  "active_minutes": 275,
  "school_lessons": 6,
  "tasks_done": 86,
  "errors_reviewed": 24,
  "retries": 17,
  "active_days": 4,
  "by_day": { "mon": 45, "tue": 55, "thu": 90, "sat": 85 }
}
```

UI родителя рендерит из этого ответа виджет и экран «Посмотреть подробнее».

## 4. Продуктовый фрейминг (обязательное ограничение)

Виджет **не оценивает** ребёнка как «успешен / неуспешен» и не показывает оценок и рейтингов.
Он показывает **факт труда** и делает невидимую работу заметной. Поэтому:

- единицы — нейтральные и «родительские»: часы, «школьные уроки», задания, дни;
- нет сравнения с другими детьми, нет «нормы», нет красных индикаторов;
- тон — поддерживающий: «ребёнок уже вложил заметный труд».

Это сохраняет позитивный контекст и убирает риск, что виджет превратится в инструмент давления.

## 5. Как проверяем гипотезу (метрики и A/B)

**Дизайн:** A/B на родителях детей с активностью за 7–30 дней, без полного доступа
(или с незавершённым решением о покупке).

| Группа | Что видит |
|---|---|
| **Control** | Текущий кабинет: программа, задания, ошибки, баннер полного доступа |
| **Test** | Тот же кабинет + виджет недельного объёма работы + экран детализации расчёта |

| Метрика | Определение | Тип |
|---|---|---|
| **ΔCR в полный доступ** | `CR(test) − CR(control)` по переходу к полному доступу | **Главная** |
| Intent | Переход на экран полного доступа / тарифов в течение 7 дней | Опережающая |
| Понимание | Доля родителей, способных назвать, сколько ребёнок занимался за неделю (опрос) | Опережающая |
| Health-guard | Отписки / жалобы / скрытие виджета | Контр-метрика (не должна расти) |

**Критерий успеха:** `CR(test) − CR(control) > 0` статистически значимо при контроле health-guard.

Опережающие метрики (Intent, Понимание) отражают воронку слайда гипотез
`Данные → Перевод → Осознание → Интерес → Действие` и показывают, на каком шаге воронка рвётся,
если главная метрика не сдвинулась.

## 6. Последствия

**Плюсы**
- Активное время меряется близко к реальному труду, устойчиво к «открытой вкладке».
- Агрегат `(child_id, week_id)` дёшев для чтения виджетом; сырьё позволяет пересчёт при смене правил.
- Единый источник правды для виджета, экрана деталей и A/B-аналитики.

**Минусы / риски**
- Heartbeat повышает трафик событий → нужен батчинг и разумный `HB`.
- Пороги `IDLE_THRESHOLD` и `LESSON_MINUTES = 45` — продуктовые допущения; калибруются на данных.
- Приватность: события об активности ребёнка → хранить агрегат, ограничить доступ, соблюдать 152-ФЗ.

**Открытые вопросы**
- Точное значение `IDLE_THRESHOLD` и определение «активности» на разных типах заданий.
- Нужен ли ребёнку явный индикатор, что время считается (прозрачность vs давление).
